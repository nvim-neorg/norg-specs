# Norg v2 Specification

  This is a draft for the Norg v2 file format specification.

  Norg's design is centered around a core driving principle -- that markup-written notes are an intermediate representation from your
  brain to a machine. They take the messy thoughts and human necessities (TODOs, tasks) and iteratively layer on more structure from
  which data can be extracted by a computer.

  This core principle is applicable to the design of the format itself: Norg is
  ultimately a vessel for converting to other file formats or representations: calendar
  formats, web pages, visualization tools; as well as for producing structure by itself: links, definitions, tables etc. 

  This means that Norg must satisfy three underlying conditions:
  1. It must be able to represent text (human -> computer interface)
  2. It must be able to annotate text with data (Norg as a vessel for other formats)
  3. It must be able to perform computations over text (producing structure)

  It does so with three primitives:
  1. Raw text
  2. Attributes
  3. Macros

  The rest of this document explains how Norg abstracts its syntax layer by layer
  -- from the lowest level macros to a regular, markdown-looking representation.

## Definitions

### Keywords

  The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
  "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and
  "OPTIONAL" in this document are to be interpreted as described in
  BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all
  capitals, as shown here.

  The words have the meanings specified below only when they are in all
  capitals. When these words are not capitalized, they have their normal
  English meanings and are not affected by this document.

  1. **MUST** -- This word, or the terms "REQUIRED" or "SHALL", mean that the
     definition is an absolute requirement of the specification.

  2. **MUST NOT** -- This phrase, or the phrase "SHALL NOT", mean that the
     definition is an absolute prohibition of the specification.

  3. **SHOULD** -- This word, or the adjective "RECOMMENDED", mean that there
     may exist valid reasons in particular circumstances to ignore a
     particular item, but the full implications must be understood and
     carefully weighed before choosing a different course.

  4. **SHOULD NOT** -- This phrase, or the phrase "NOT RECOMMENDED" mean that
     there may exist valid reasons in particular circumstances when the
     particular behavior is acceptable or even useful, but the full
     implications should be understood and the case carefully weighed
     before implementing any behavior described with this label.

  5. **MAY** -- This word, or the adjective "OPTIONAL", mean that an item is
     truly optional. One vendor may choose to include the item because a
     particular marketplace requires it or because the vendor feels that it
     enhances the product while another vendor may omit the same item. An
     implementation which does not include a particular option MUST be
     prepared to interoperate with another implementation which does include
     the option, though perhaps with reduced functionality. In the same vein
     an implementation which does include a particular option MUST be
     prepared to interoperate with another implementation which does not
     include the option (except, of course, for the feature the option
     provides.)

## Layer 0: The AST

  - `=macro` - defines a macro
  - `@macro` - invokes a macro with raw, non-markup content
  - `|macro` - invokes a macro with markup content
  - `:macro` - invokes a macro with raw, non-markup content but allows escape characters inside (quasi-quoting)
  - `&macro` - textually expands a macro, replacing itself with the contents of the macro

  The rest of the file format is derived by creating syntax elements that are shorthands for these macros.

  Text is inherently impossible to represent. We make assumptions about:
  - Direction of text flow
  - How paragraphs are chunked
  - Dimensional representation (lists, tables)

  For this reason, the following standard library of macros is defined:
  - `flow direction` - describes in which direction elements should move. document creation is constructive, so only two possible values: down, right.
  - `block` - describes a group of objects. necessary to establish unambiguous directional flow.
    - `block-break` - creates a visible divider between two blocks.
  - `line` - describes a line, which may contain text.
  - `inline` - describes text, can embody styling elements for the text.
    - `char` - describes a character of some type
    - `whitespace` - describes a whitespace character
    - `style name` - styles a body of text in a specific way. needs an internal secondary `|inline` for further styling

  This list of macros is sufficient to foundationally represent any Norg document (extra features are representable using custom macros).

  Layer 0 uses the unhygienicness of macros to inject parameters that other
  macro invocations require. For example, `|flow` expects a parameter
  `direction` to determine its direction - thus it is defined above the macro.
  A macro definition will shadow an earlier definition with the same name.
  A nonexistent macro is an error.

  Example document:

## Layer 1

  Layer 1 is interested in bootstrapping easier to use macros. To achieve this, we introduce the following syntaxes:

  - `@macro param` and `|macro param` - functionally equivalent to:
    ```
     =param
       value
     =end

     |macro
       <content>
     |end
    ```
  - `=macro param` - functionally equivalent to:
    ```
     =param
       value
     =end

     =macro
       <content>
     =end
     ```
  - as well as the one-line macro syntax:
    `.macro value1 value2`
    which is equivalent to:
    ```
      |macro value1 value2
      |end
    ```
  - we also introduce the carryover tag:
  ```
  #macro value1 value2
  object
  ```
  which is equivalent to:
  ```
    =param_name_1
      value1
    =end
    =param_name_2
      value2
    =end
    |macro
      &object
    |end
  ```
  where the parameter names are inferred automatically from the original macro's definition.
  Carryover tags always expand to a non-verbatim macro (`|macro`).

  ```
  #flow down
  |block
    #flow right
    |block

## Layer 3: Implicit Char Wrapping

Introduces new `|span` macro.

A bare word (a sequence of non-whitespace, non-special characters) appearing
inside a `|span` context is implicitly treated as a sequence of `char`
invocations inside of an `|inline` macro - one per Unicode scalar value.

`|inline` must still be used when styling and stitching text in non-traditional ways.

```
#flow right
|block
  |inline
    #style bold
    |span
      Hello
    |end

    .whitespace

    #style italic
    |span
      world
    |end
  |end
|end

.block-break

|block
  |span
    Beside
  |end
|end
```

## Layer 4: Implicit Block Boundaries

Blocks are automatically opened at the beginning of the document and after every block break and closed by the `block-break` directive.

```
#flow right

    |span
      Hello
    |end

    .whitespace

    #style italic
    |span
      world
    |end
  |end
|end

.block-break

|span
  Beside
|end
```

## Layer 6: Implicit `|inline`

Immediately adjacent spans and whitespace are implicitly wrapped in a single `|inline`.
Styled spans are wrapped in `|style` and do not get implicitly wrapped together. An inline
block may begin with a style, but may not contain multiple styles within itself via this rule. 

```
#style bold
|span
  Hello
|end

.whitespace

#style italic
|span
  world
|end

.block-break

|span
  Beside
|end
```

## Layer 7: Implicit Span

All consecutive text elements which do not constitute a macro invocation are greedily and implicitly collected
into a `|span`.

```
#style bold
|span
  Hello
|end

.whitespace

#style italic
|span
  world
|end

.block-break

Beside
```

## Layer 8: Attached Modifiers

Introduces shorthand sigil pairs that expand to `#style` carryover tags
wrapping any `|inline` block. An attached modifier is *opening* if its opening
sigil is immediately adjacent to its content (whitespace or the start of the
inline block before the sigil, no whitespace after the sigil) to the first
character of its content. An attached modifier is *closing* if its closing sigil
is immediately adjacent to the end of the inline block or whitespace (content
directly before the closing sigil, whitespace or block-break immediately
afterwards).

```
*Hello*

.whitespace

/world/

.block-break

Beside
```

## Layer 9: Implicit Whitespace

A literal space or tab character appearing between elements at any inline
context level inside `|span` is implicitly treated as a `whitespace` node. The
explicit `whitespace` form remains available for edge cases where the source
character is not a literal space. Multiple empty lines produce multiple block
breaks.

```
*Hello* /world/

.block-break

Beside
```

## Layer 10: Implicit Block Breaks

Blank lines in the source document are treated as implicit block breaks. A
blank line is defined as a line containing no non-whitespace characters.

```
*Hello* /world/

Beside
```

# Syntax Reference

This document reconstructs Norg's surface syntax in terms of the macro primitives defined in the v2 specification.

## Primitive Invocation Types

Three primitive invocation types exist at Layer 0:

| Sigil                  | Name        | Content model                                | Terminates  |
|------------------------|-------------|----------------------------------------------|-------------|
| `\|macro ... \|end`    | markup      | Body parsed as Norg markup                   | `\|end`     |
| `@macro ... @end`      | raw         | Body is opaque text; nothing parsed           | `@end`      |
| `:macro ... :end`      | quasiquote  | Body is raw text; `\` introduces escapes     | `:end`      |

And one definition form:

| Sigil               | Name       | Effect                              |
|---------------------|------------|-------------------------------------|
| `=macro ... =end`   | definition | Binds a name to content             |

The **one-line invocation** is:

```
.macro value1 value2
```

which is equivalent to:

```
|macro value1 value2
|end
```

---

## The Quasiquote Invocation (`:macro ... :end`)

A quasiquote invocation's body is raw text — it is not scanned for macro
invocations or markup — but the backslash `\` introduces escape sequences
that are interpreted before the body is passed to the macro.

### Directionality of the three types

```
|macro   active (markup)   ─── content is Norg, fully parsed
:macro   quasiquote        ─── content is raw, but \ escapes to char scalars
@macro   raw               ─── content is opaque; nothing is processed
```

The quasiquote is consistently "inert → more inert": it starts at the raw
string level and its escape mechanism descends to the Unicode scalar level
beneath it. It does not grant access upward to Norg markup. A macro that
genuinely needs both markup and raw content in its body must be invoked
with `|macro` and use nested `@macro` invocations inside.

### Why math is `@` and verbatim is `:`

`$math$` uses `@span` because the content is LaTeX, which has its own `\`
escape system. Intercepting `\` at the Norg layer would corrupt LaTeX
expressions before they reach the math renderer. Math must be fully sealed.

`` `verbatim` `` uses `:span` because verbatim's own terminator (`` ` ``)
can legitimately appear inside code or prose being quoted. The `\`` escape
allows a literal backtick without ending the span. This is the only
processing verbatim content undergoes: escape resolution. It never becomes
markup, and no Norg constructs are recognised inside it.

### Verbatim with escape: `` `hello \`world` ``

The body of a verbatim span is `:span` (quasiquote). The escape `\`` resolves
to a literal backtick at the character-scalar level before the content is
handed to `verbatim`.

**Surface:**
```
`hello \`world`
```

**Attached modifier expansion:**
```
#style verbatim
:span
  hello \`world
:end
```

**Carryover expansion (Layer 1):**
```
=name
  verbatim
=end
|style
  :span
    hello \`world
  :end
|end
```

**Layer 0:**
```
=name
  verbatim
=end
|style
  :span
    hello \`world
  :end
|end
```

No `|char` expansion occurs. The quasiquote body is passed to `verbatim`
as a resolved character sequence (`` hello `world ``) after escape processing.
The macro system does not look inside it further.

**Contrast — verbatim without escape need:** `` `printf()` ``

```
=name
  verbatim
=end
|style
  :span
    printf()
  :end
|end
```

No escapes needed; the body contains no `:end` or `\` sequences.

**Layer 1:**
```
=name

|end

```
#link https://example.com

```

## Custom Ranged Tags

Unrecognised `@tag` or `|tag` invocations are passed to user-defined or
renderer-defined macro handlers. Raw-body tags use `@`; markup-body tags
use `|`; quasiquote-body tags use `:`.

**Raw (opaque body):**
```
@table csv
Name, Age
Alice, 30
@end
```

**Markup body:**
```
|note
  This is an *important* note.
|end
```

**Quasiquote body (with escape):**
```
:template
  Dear \: friend,
  Your invoice is due\:
:end
```

The `:` in the quasiquote body is escaped via `\:` wherever a literal
colon might otherwise be ambiguous, and `\:end` produces a literal `:end`
without terminating the block.
